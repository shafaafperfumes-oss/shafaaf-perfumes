# Shafaaf Perfumes — Website Quality Audit
**Date:** 2026-09-21 · **Agent:** website-agent · **Scope:** repo code review + live site (https://shafaaf-perfumes.shafaafperfumes.workers.dev), no sign-in, no SEO/meta/JSON-LD (covered elsewhere).

Catalog checked against: 14 fragrances (Perfume + Attar each) + 5 bakhoor = 19 products, confirmed live on `/shop.html` ("19 fragrances" — see finding S-1).

---

## 1. Site-wide (loaded on every page)

### 🔴 Product ratings and reviews shown to customers are entirely fabricated
- **File:** `js/data/reviews.js` (whole file) + `js/data/products.js` (`rating`/`reviewCount` fields on every product) + rendered in `js/components/product-card.js:47`, `js/components/quick-view.js:29`, `js/pages/home.js:63/77`, `js/pages/product.js:72,174-176`.
- **What's wrong:** Every star rating, review count, reviewer name and review text on the site is procedurally generated placeholder data (`shafaafGetProductReviews()` picks from a 5-name pool seeded by product id — see `js/data/reviews.js:47-71`). It is clearly labelled "mock" in code comments, but nothing on the page tells a visitor that. The 5 homepage testimonials (`js/data/reviews.js:9-40`) even give reviewers Pakistani cities (Lahore, Karachi, Islamabad, Faisalabad, Multan) for a brand that ships nationwide **India** — a customer who notices this will lose trust immediately. This also conflicts with BRAND.md rule 4 ("no made-up reviews").
- **Proposed change:** Until a real reviews system exists, either (a) remove star ratings/review counts from cards and PDP entirely, or (b) keep them but change the testimonial names' locations to Indian/Kashmiri cities and add a small "based on customer feedback" style disclaimer. This needs an owner decision — do not silently keep shipping fake numbers as real.

### 🔴 Newsletter forms collect nothing
- **Files:** `js/main.js:13-23`; forms at `index.html:253-256` & `:301-304`, `about.html:113-116` & footer, and the same footer form on every other page.
- **What's wrong:** Submitting the "Join the Shafaaf Circle" email form shows a success toast ("Thanks for subscribing — welcome to Shafaaf.") and calls `shafaafTrackEvent`, but that function only `console.debug`s on `localhost`/`file:` (`js/main.js:7-11`). On the live site the email is never sent anywhere or stored — it's thrown away, while the customer is told they subscribed. This is a false success message on every page.
- **Proposed change:** Either wire the form to a real endpoint (e.g. a Supabase table or a simple email-capture service) before the owner starts telling customers to subscribe, or remove the newsletter forms until that backend exists.

### 🟡 "Add to cart" bag icon on product cards doesn't add to cart
- **File:** `js/components/product-card.js:51`.
- **What's wrong:** `aria-label="Add {name} to cart"` on the bag-icon button, but the button is wired to `data-quick-view` (opens the Quick View modal, not an add). A screen-reader user or anyone reading the label will expect an instant add; they get a modal instead (the real "Add to Cart" button lives inside that modal, `js/components/quick-view.js:51`).
- **Proposed change:** Change the label to `aria-label="Quick add {name}"` or `"View options for {name}"` so it matches what actually happens.

### 🟡 Checkout requires an account — no guest checkout
- **File:** `js/pages/checkout.js:44-52` (`renderSignedOut`).
- **What's wrong:** A shopper with items in the bag who reaches checkout is stopped and told to "Sign in (or create an account)" before they can pay — there is no guest-checkout path. Forced account creation is one of the best-known cart-abandonment causes in e-commerce.
- **Proposed change:** Not a quick fix (it's how the backend/account system is built), but worth flagging to the owner as a real lost-sales risk to weigh against the effort of adding guest checkout later.

### 🟢 20 separate `<script>` tags per page, unminified CSS/JS
- **Files:** every page's script block (e.g. `index.html:378-401`) and `css/*.css`.
- **What's wrong:** Each page loads ~20 individual JS files plus 5 CSS files, none bundled or minified (`css/components.css` alone is 33KB uncompressed, shared but mostly used on only some pages). This is fine functionally (scripts sit at the end of `<body>`, so nothing blocks first paint) but it's ~25 HTTP requests before the page is interactive, which is slow on weak mobile connections common in Kashmir.
- **Proposed change:** No urgency now; when there's backend/build tooling in place, bundle+minify JS/CSS into one file per page as a later speed pass. Do **not** touch product photos for this — only code files.

### 🟢 `logo-mark.png` is 337KB for a header logo
- **File:** `images/logo-mark.png` used at `index.html:24` etc. with `width="538" height="640"`, displayed at a few dozen pixels tall via CSS.
- **What's wrong:** It's cached after first load so the repeat-page cost is low, but the first page a visitor lands on pays for a 337KB PNG for what renders as a small logo mark.
- **Proposed change:** This is a **logo/design asset, not a product photo** — the no-resize rule protects product photography, not this. If the owner is open to it, a lossless PNG→WebP conversion (same pixels, smaller file) would cut this a lot. Flagging only — not done without approval since it is still an image file.

### 🟢 Unused image files inflate the repo
- **Files:** `images/ameer-al-oud-gold-attar.jpg`, `images/ameer-al-oud-gold-perfume.jpg`, `images/amber-oud.jpg` are not referenced by `js/data/products.js` or any HTML/JS (confirmed by search) — they appear to be superseded versions after a re-shoot, but they are still being deployed live (verified `ameer-al-oud-gold-attar.jpg` returns 200 on the live site).
- **Proposed change:** No urgency; if the owner confirms these are old/replaced shots, they can be deleted later to keep the images folder tidy. Not touching without explicit confirmation per rule "never delete a file without confirmation."

### 🟢 `.assetsignore` doesn't list `images/_originals/`
- **File:** `.assetsignore`.
- **What's wrong:** The 50MB `images/_originals/` working folder isn't in the ignore list the way `backend/`, `scripts/`, `.claude/` are. Checked live: `images/_originals/khamra-qahwa.png` currently 404s, so it does **not** appear to be deployed today — but that's relying on undocumented Cloudflare behaviour, not an explicit exclusion.
- **Proposed change:** Add `images/_originals/` to `.assetsignore` explicitly so this stays true on purpose, not by accident.

## 2. Homepage (`index.html`)

### 🟢 "Featured Collections" only shows 3 of 7 families
- **File:** `index.html:96-108` (`#collection-grid`, populated by JS).
- **What's wrong:** Live page shows only Oud, Floral, Gourmand tiles even though the catalog spans 7 families (Oud, Musk, Floral, Gourmand, Fresh, Woody, Spicy per brand brief). Likely intentional curation, not a bug — flagging in case it's meant to rotate/expand and hasn't been revisited since Bakhoor and newer families were added.

### 🟢 Spotlight image is marked `eager` despite being far below the fold
- **File:** `js/pages/home.js:59` (`shafaafProductMedia(p, { eager: true })` for the "Signature Spotlight" section, which sits near the bottom of the homepage, after Best Sellers/Offers/Story/Discovery).
- **What's wrong:** `eager` skips `loading="lazy"` (see `js/components/placeholder-art.js:55`), so this off-screen image downloads immediately with the rest of the page instead of only when scrolled near. Wastes initial bandwidth on mobile; there is no true LCU-critical image on the homepage (the hero is pure CSS, no `<img>`), so nothing needs to be eager here.
- **Proposed change:** Remove `{ eager: true }` at `js/pages/home.js:59` so this image lazy-loads like the rest of the grid.

### 🟢 Story stats don't mention Bakhoor
- **File:** `index.html:148-161` (`14 Fragrances / 2 Formats Each / 7 Fragrance Families`).
- **What's wrong:** Accurate as far as it goes (14 fragrances is correct), but doesn't reflect that the catalog now also has a 5-item home-fragrance (Bakhoor) line — a missed chance to show the fuller 19-product range.
- **Proposed change:** Optional 4th stat tile, e.g. "5 · Bakhoor Scents", if the owner wants the stats to represent the whole catalog.

## 4. Shop page (`shop.html`)

### 🟡 "19 fragrances" count includes Bakhoor, which the rest of the site calls a separate category
- **File:** `js/pages/shop.js:196`.
- **What's wrong:** When no type filter is active, the result count reads `"19 fragrances"`. Everywhere else on the site (nav, footer, shop-by-type tiles) Bakhoor is deliberately kept as its own category, distinct from "fragrances" — so labelling the unfiltered total "19 fragrances" is slightly imprecise (5 of those 19 are bakhoor jars, not fragrances).
- **Proposed change:** When unfiltered, show a neutral word instead, e.g. `"19 products"` — one-line change: swap the fallback `"fragrance" + (total !== 1 ? "s" : "")` for `"product" + (total !== 1 ? "s" : "")` at `js/pages/shop.js:196`. (When a type filter *is* active it already correctly says "14 Perfumes" / "5 Bakhoor" etc., so no change needed there.)

## 5. Product detail page (`product.html` / `js/pages/product.js`)

### 🟡 Main gallery image has no `fetchpriority` or size hints
- **File:** `js/pages/product.js:47-48` (`renderGallery`) — `<img id="pdp-main-img" src="...">`.
- **What's wrong:** This is the largest, most important image on the most conversion-critical page (the product photo shoppers are deciding on) and is very likely the Largest Contentful Paint element on `product.html`, yet it has no `fetchpriority="high"`, and no `width`/`height` attributes (the CSS does reserve space via `.pdp-gallery__main`/aspect-ratio in most themes, but explicit attributes are a cheap belt-and-braces fix that also help before CSS loads).
- **Proposed change:** `<img id="pdp-main-img" src="..." alt="..." fetchpriority="high" width="800" height="1000">` (adjust width/height to the real photo's aspect ratio — no resizing of the file itself, just declaring its dimensions in HTML).

### 🟡 Placeholder-art products missing photos: Dubai Oud, Summer Oud, Silver Scent
- **File:** `js/data/products.js:151-204` — `image: null` for these three.
- **What's wrong:** Confirmed intentional per code comments and prior project notes (photos pending), not a bug — they correctly fall back to the generated monogram-bottle illustration (verified live on `product.html?id=dubai-oud`). Listing here only so it's tracked in one place: 3 of 14 fragrances still need real photography.

## 6. Thin product descriptions — proposed editorial copy
